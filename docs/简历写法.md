- 接入 Allure 报告与 GitHub Actions，失败自动附请求/响应/截图/页面 HTML；支持 `pytest -m smoke` 冒烟回归。

**项目描述**：为自研迷你电商系统 ShopLite 建立可持续执行的自动化测试体系，解决手工回归重复、接口与页面数据不一致、缺陷定位慢的问题。

**主要工作**：

1. **测试设计**：梳理登录、商品、购物车、优惠券、下单、订单六条业务链路，输出测试计划与 57 条用例，使用等价类、边界值、场景法、错误推测补充异常场景。

5. **工程化**：接入 Allure 报告、日志、PyCharm 运行配置和 GitHub Actions；支持按 `smoke`、`api`、`ui` 标记分组执行。

**项目成果**：全量 57 条用例本地执行通过，单次全量约 30 秒；冒烟集 6 条约 7 秒；失败用例可通过 Allure 直接定位到请求、响应、截图和数据库结果。

## 3. 高频面试题与回答

### Q1：为什么选 pytest，不选 unittest？

pytest 的 fixture 可以按 session/function 控制作用域，参数化和插件生态更好，断言失败信息更直观。比如这个项目用 session 级 fixture 只启动一次服务，用 function 级 fixture 给每个用例建独立用户，unittest 的 setUp/tearDown 做起来会更啰嗦。

### Q2：fixture 的作用域怎么设计的？

- `demo_server`、`browser` 是 session：启动成本高，整个会话复用；
- `api`、`user`、`auth_api`、`page` 是 function：每个用例独立，避免 token、Cookie、购物车串数据；
- `db_path` 是 session：跟服务共用同一个临时数据库。

原则：**贵的资源复用，脏的数据隔离。**

### Q3：token 怎么管理的？

登录成功后把 token 放到 `requests.Session.headers["Authorization"]`，后续请求自动携带。客户端只负责“带 token”，不负责“断言 token 对不对”；断言在用例里。

### Q4：用例之间怎么做数据隔离？

两层：

1. 每个用例注册一个随机用户 `qa_xxx`，购物车和订单按 user_id 隔离；
2. 整个测试会话用临时 SQLite，跑完删除，不污染开发数据。

所以用例顺序变化、单独执行、重复执行都不受影响。

### Q5：为什么既断言接口又查数据库？

接口返回 201 只代表“接口说成功了”，不代表订单真的写进库。比如开发可能返回一个假订单号，或者只写主表没写明细。项目里会查 `orders`、`order_items`，并确认库存扣减，避免假通过。

### Q6：JSON Schema 校验解决什么问题？

它保证接口契约稳定：字段必填、类型正确、金额是整数、订单号格式正确。只断言几个字段，接口把 `price_cents` 从整数改成字符串时可能发现不了。

### Q7：UI 自动化为什么用 Page Object？

把“怎么找元素、怎么点”封装在页面对象里，用例只写业务动作。页面改版时只改 Page Object，不改几十条用例；同时用例可读性更好。

### Q8：UI 用例为什么这么少？

UI 执行慢、受页面影响大，适合覆盖关键用户旅程；大量规则、异常、边界放在接口层，符合测试金字塔。这个项目 UI 覆盖 13 条关键路径，接口覆盖 41 条规则和异常。

### Q9：怎么解决 UI 用例不稳定？

- 统一 `data-testid`，不依赖样式和层级；
- 用 Playwright 自动等待，页面对象里等待 URL/元素，不用 `sleep`；
- 每个用例独立浏览器 Context，避免 Cookie 污染；
- 失败自动截图 + 保存 HTML，先定位再改，不靠“重跑就过”。

### Q10：项目里最难的点是什么？

不是写某一条用例，而是**让整套测试可重复执行**：服务要自动起停、数据库要隔离、每个用例要有独立用户、UI 要等待正确、失败要能定位。这些工程问题解决了，用例才有价值。

### Q11：怎么判断一个接口用例写得合格？

至少满足：

1. 有明确的业务预期，不是只断言 200；
2. 覆盖成功和失败；
3. 关键字段有断言；
4. 数据有落库校验（涉及写操作时）；
5. 失败信息能定位到请求和响应；
6. 不依赖其他用例的执行顺序。

### Q12：如果让你测“并发下单扣库存”，怎么设计？

先说明当前项目是单线程 SQLite，没覆盖并发。思路：

1. 准备库存为 1 的商品；
2. 用线程池/压测工具同时发 N 个下单请求；
3. 断言只有一个成功，其余返回库存不足；
4. 查库确认库存不为负、订单数与成功数一致；
5. 需要数据库行锁/乐观锁/事务支持，SQLite 要换 MySQL/PostgreSQL 更合适。

这样回答既承认边界，又展示设计能力。

### Q13：为什么自己写被测系统，不测公开网站？

公开网站会挂、会限流、会改版，面试当天跑不起来很致命；自己写的系统能精确控制业务规则，才能设计“刚好满 100 元”的优惠券边界，也能同时做数据库断言。真实工作中被测系统是公司的，但测试方法是一样的。

### Q14：CI 里怎么跑？

GitHub Actions 每次 push/PR：安装依赖 → 安装 Chromium → 跑 pytest → 上传 Allure 结果 → 生成报告。CI 环境用 `SHOPLITE_BROWSER=chromium`，本地默认用已安装的 Edge，避免重复下载浏览器。

### Q15：这个项目有什么不足？

主动说：

- 没有真实支付、并发扣库存、分布式事务；
- 数据库是 SQLite，不是 MySQL；
- UI 只覆盖 Chromium/Edge，没有多浏览器矩阵；
- 没有性能和安全测试；
- 用例量还不大，后续可以接 xdist 并行和更大规模的数据驱动。

## 4. 面试现场演示顺序（5 分钟）

1. 打开 PyCharm，展示目录结构，讲三层：`tests` / `pages` / `framework`；
2. 打开 `tests/api/test_orders.py`，讲一条“下单 + 数据库断言”的用例；
3. 运行 `pytest tests/api/test_orders.py -v`，现场看通过；
4. 打开 Allure 报告，展示请求、响应、步骤；
5. 打开 `tests/ui/test_login.py`，运行一条 UI 用例；
6. 讲 CI 文件和测试文档。

不要一上来跑全量，先跑一条最有代表性的接口用例，节省时间。

## 5. 简历里不要写的内容

- ❌ “精通 Python / 精通自动化测试” → 改成“熟悉 pytest、requests、Playwright，能独立搭建分层框架”
- ❌ “覆盖率 100%” → 除非你真的统计了代码覆盖率
- ❌ “发现 100 个 Bug” → 没有缺陷跟踪记录就不要写数字
- ❌ “搭建测试平台” → 这个项目是测试框架，不是平台，别混
- ❌ 把被测系统说成“公司项目” → 面试官一问业务细节就穿帮
- ❌ 写“熟练 Selenium”但项目里是 Playwright → 会什么写什么
