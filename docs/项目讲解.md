# 从零看懂 ShopQA：这套自动化测试是怎么写出来的

> 这篇是写给你自己看的“项目说明书”。  
> 不用背代码，先记住一句话：**自动化测试 = 用代码把“人怎么点、怎么验”固定下来，让机器重复执行。**

---

## 0. 先看全貌：这个项目到底在干什么

把项目想成一家小商店：

- `app/` 是商店本身（被测系统）；
- `tests/` 是质检员（测试用例）；
- `pages/` 是质检员的“操作手册”（页面对象）；
- `framework/` 是质检员的工具（请求客户端、断言、配置）；
- `reports/` 是质检报告。

一次完整测试的流程：

```text
pytest 启动
  → 自动启动 ShopLite 服务
  → 自动建一个临时数据库
  → 接口用例：直接调 API，查数据库
  → UI 用例：打开浏览器，像用户一样点击
  → 生成 Allure 报告
  → 关服务、关浏览器、删临时数据
```

你不需要先开服务、先建数据库、先准备账号。**测试自己准备一切，这叫“测试自治”。**

## 1. 第 1 步：先写一个能跑的业务系统

测试不能对着空气写。先有一个最小闭环：

```text
登录 → 看商品 → 加购物车 → 结算 → 下单 → 看订单
```

对应文件：

```text
app/main.py       页面路由 + JSON API
app/db.py         建表、种子数据、密码哈希
app/templates/    页面 HTML
```

关键设计：

1. **价格用“分”存整数**  
   `89.00 元` 存成 `8900`。浮点数做金额计算会出现 `0.1 + 0.2 = 0.30000000000000004`，测试断言会很痛苦。

2. **每个页面元素加 `data-testid`**  
   比如登录按钮：

   ```html
   <button data-testid="login-submit">登录</button>
   ```

   测试里用 `get_by_test_id("login-submit")`，不依赖 `div > form > button:nth-child(2)` 这种一改版就失效的选择器。

3. **接口和页面共用一套业务逻辑**  
   UI 的“提交订单”和 API 的 `POST /api/orders` 最后都调用 `place_order()`。  
   这样不会出现“页面能下单、接口不能下单”的两套逻辑。

4. **业务错误返回 4xx，不返回 500**  
   库存不足、优惠券不可用、购物车为空，都是用户可以处理的错误，返回 400 并给明确提示。

## 2. 第 2 步：先手工走一遍，再写自动化

打开：

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

浏览器访问 <http://127.0.0.1:8000>，用 `demo / Demo123!` 登录，完整下一单。

手工走的时候，拿张纸记下三件事：

1. **我点了什么**：输入框、按钮、链接；
2. **我看到了什么**：金额、提示、订单号；
3. **什么情况会出错**：密码错、库存不够、优惠券不满 100、购物车为空。

这三件事，就是后面测试用例的“步骤”和“预期结果”。

> 新手最容易犯的错：一上来就写代码。  
> 正确顺序是：手工走通 → 写清用例 → 再自动化。自动化只是执行手段，不是测试设计本身。

## 3. 第 3 步：把测试代码分层

先看目录：

```text
tests/          用例：只写“做什么、验什么”
pages/          页面对象：只写“怎么点”
framework/      工具：请求、断言、配置、日志
data/           数据：账号、优惠券、搜索关键字
```

为什么分层？举个例子。

**不分层**的用例：

```python
def test_login():
    requests.post("http://127.0.0.1:8000/api/auth/login", json={...})
    # 又夹着 CSS 选择器、数据库连接、断言
```

**分层后**的用例：

```python
def test_login_and_me(api, user):
    response = api.login(user["username"], user["password"])
    assert_status(response, 200)
    assert api.get("/api/auth/me").json()["username"] == user["username"]
```

用例读起来像一句业务话。  
面试官问“你的框架怎么分层”，你就讲这三层。

## 4. 第 4 步：fixture 负责“准备工作”

`tests/conftest.py` 是 pytest 的公共夹具文件。夹具（fixture）就是“用例开始前帮你准备好的东西”。

这个项目里最关键的几个：

| fixture | 作用 | 作用域 |
|---|---|---|
| `demo_server` | 启动被测服务，返回地址和临时数据库 | session（整个测试会话一次） |
| `api` | 创建一个 requests 客户端 | function（每个用例一个） |
| `user` | 注册一个随机用户 | function |
| `auth_api` | 登录后的客户端 | function |
| `browser` | 启动浏览器 | session |
| `page` | 新建一个干净浏览器上下文和页面 | function |
| `login_as` | API 建用户 + UI 真实登录 | function |

### 为什么要随机用户

如果所有用例都用 `demo`，A 用例加了购物车，B 用例一查就多了一件，测试顺序一变就失败。

所以：

```python
username = f"qa_{uuid.uuid4().hex[:10]}"
```

每个用例一个全新用户，购物车、订单天然隔离。

### 为什么数据库是临时的

`demo_server` 里：

```python
temp_dir = Path(tempfile.mkdtemp(prefix="shoplite-"))
db_path = temp_dir / "shoplite.db"
env["SHOPLITE_DB_PATH"] = str(db_path)
```

每次跑测试都建一个新数据库，跑完就扔。  
好处：不污染开发数据、不需要手工清库、用例可以放心下单。

### 为什么服务只启动一次

启动服务要一两秒，56 条用例每条启动一次太慢。  
所以 `demo_server` 用 `scope="session"`，整个会话只启动一次；但每个用例仍然用独立用户，兼顾速度和隔离。

## 5. 第 5 步：封装 API 客户端

文件：`framework/api_client.py`

它只做三件事：

1. 自动拼 base URL；
2. 自动带 token；
3. 把请求和响应写进日志、挂到 Allure。

核心代码简化后：

```python
class ApiClient:
    def __init__(self, base_url):
        self.base_url = base_url
        self.session = requests.Session()

    def set_token(self, token):
        self.session.headers["Authorization"] = f"Bearer {token}"

    def request(self, method, path, **kwargs):
        response = self.session.request(method, f"{self.base_url}{path}", **kwargs)
        allure.attach(response.text, name="response")
        return response
```

为什么用 `requests.Session`？

- 自动复用 TCP 连接；
- 自动管理 Cookie；
- 可以统一设置 headers。

为什么不在客户端里 `assert`？

因为客户端是“工具”，不同用例的预期可能不同。  
断言放在测试里，失败信息才清楚。

## 6. 第 6 步：写第一条接口用例

文件：`tests/api/test_auth.py`

```python
@allure.title("登录成功返回 token，并能用 token 获取当前用户")
@pytest.mark.smoke
def test_login_and_me(self, api, user):
    response = api.login(user["username"], user["password"])

    assert_status(response, 200)
    assert_schema(response.json(), LOGIN_SCHEMA, "登录响应")
    assert response.json()["token_type"] == "bearer"

    me = api.get("/api/auth/me")
    assert_status(me, 200)
    assert me.json()["username"] == user["username"]
```

这条用例其实在验四件事：

1. 登录接口返回 200；
2. 响应结构符合契约（有 token、token_type、user）；
3. token 类型是 bearer；
4. 拿这个 token 能取到当前用户。

### 断言为什么要分层

只写 `assert response.status_code == 200` 是不够的。  
接口可能返回 200，但 `access_token` 是空字符串，或者用户 ID 是别人的。

所以项目里用了三种断言：

| 断言 | 作用 | 例子 |
|---|---|---|
| 状态码 | 先确认请求成功/失败类型 | 201、400、401、404、422 |
| 子集断言 | 只验关心的字段 | `detail == "用户名已存在"` |
| JSON Schema | 验完整结构和类型 | `price_cents` 必须是整数 |

## 7. 第 7 步：数据驱动，不要把用例写成复制粘贴

文件：`data/api_cases.yaml`

```yaml
invalid_registrations:
  - case_id: AUTH-REG-01
    title: 用户名只有 2 个字符
    username: ab
    password: Passw0rd!
    expected_status: 422
```

测试里：

```python
@pytest.mark.parametrize(
    "case",
    AUTH_CASES["invalid_registrations"],
    ids=[item["case_id"] for item in AUTH_CASES["invalid_registrations"]],
)
def test_register_validation(self, api, case):
    response = api.post("/api/auth/register", json={...})
    assert_status(response, case["expected_status"])
```

好处：

- 加一条异常数据只改 YAML，不改 Python；
- 报告里每条数据是独立用例，失败能定位到具体数据；
- 面试官问“数据驱动怎么做的”，直接打开文件给他看。

## 8. 第 8 步：数据库断言，防止“假通过”

接口返回 201，不代表订单真的写进数据库了。  
所以下单用例除了看响应，还查库：

```python
assert count(db_path, "orders", "user_id = ?", (user["id"],)) == 1
assert count(db_path, "order_items", "order_id = ?", (order["id"],)) == 1
assert stock_of(db_path, product["id"]) == stock_before - 1
```

这叫“接口 + 数据”双重验证。

面试时可以说：

> 我不仅断言接口返回，还会查订单主表、订单明细表和库存表。因为只断言响应，开发完全可以在返回体里拼一个假订单，数据库其实没写。

## 9. 第 9 步：Page Object，把“怎么点”关进笼子

文件：`pages/login_page.py`

```python
class LoginPage(BasePage):
    path = "/login"

    def login(self, username, password):
        self.locator("login-username").fill(username)
        self.locator("login-password").fill(password)
        self.locator("login-submit").click()
        return ProductsPage(self.page)
```

测试里：

```python
login_page = LoginPage(page)
login_page.goto()
products_page = login_page.login(user["username"], user["password"])
```

好处：

- 页面改版，只改 Page Object，不改几十条用例；
- 用例读起来是“登录”，不是“找 id、填值、点击”；
- 每个页面对象返回下一个页面对象，形成业务流：
  `LoginPage → ProductsPage → CartPage → CheckoutPage → OrderDetailPage`。

### 为什么用 Playwright，不用 Selenium

两个都能找工作。这个项目选 Playwright 的原因：

1. 自带自动等待，少写 `WebDriverWait`；
2. `get_by_test_id` 直接按测试 ID 查找，选择器更稳；
3. 默认无头模式，跑得快；
4. 安装比 Selenium + 驱动简单，CI 里一条命令装浏览器。

面试如果问 Selenium，你可以说：

> 我主项目用 Playwright，但 Selenium 的显式等待、Page Object、driver 管理思路是相通的；需要的话我可以迁移。

## 10. 第 10 步：写第一条 UI 用例

文件：`tests/ui/test_login.py`

```python
def test_demo_user_login(self, page):
    login_page = LoginPage(page)
    login_page.goto()
    assert login_page.is_loaded()

    products_page = login_page.login("demo", "Demo123!")
    products_page.wait_for_url("**/products*")

    assert products_page.is_loaded()
    assert products_page.text_of("current-user") == "demo"
```

它做了：

1. 打开登录页；
2. 输入账号密码；
3. 点登录；
4. 等 URL 变成商品页；
5. 断言当前用户和购物车数量。

### 失败截图怎么来的

`tests/conftest.py` 里有个 pytest 钩子 `pytest_runtest_makereport`，每个用例结束后记录结果。  
`page` 夹具在用例结束时检查：如果失败了，就截图并 attach 到 Allure。

```python
if failed:
    screenshot = page.screenshot(full_page=True)
    allure.attach(screenshot, name="失败截图", ...)
    allure.attach(page.content(), name="失败页面 HTML", ...)
```

面试官问“UI 用例失败怎么排查”，这就是答案：**截图 + HTML + 日志 + Allure 步骤**。

## 12. 如果面试官让你现场加一条用例

比如：“加一个用例，验证购物车数量不能超过 99。”

你按这个顺序说、写：

1. **设计用例**：已登录，加购 quantity=100，预期 422；
2. **找数据**：任选一个商品，拿 `product_id`；
3. **写代码**：

```python
@pytest.mark.parametrize("quantity", [0, -1, 100])
def test_invalid_quantity(self, auth_api, find_product, quantity):
    product = find_product("机械键盘 Pro")
    response = auth_api.post(
        "/api/cart/items",
        json={"product_id": product["id"], "quantity": quantity},
    )
    assert_status(response, 422)
```

4. **跑**：`pytest tests/api/test_cart.py -k invalid_quantity -v`；
5. **看报告**：确认 Allure 里有请求和响应。

这条其实项目里已经有，你可以直接演示。

## 13. 为什么这么设计（面试加分）

| 设计 | 原因 |
|---|---|
| 自带被测系统 | 不依赖外网，面试随时能跑；业务规则可控，能设计精确边界 |
| 接口为主、UI 为辅 | 接口快且稳，UI 只覆盖关键旅程，符合测试金字塔 |
| 每用例随机用户 | 数据隔离，避免顺序依赖 |
| 临时数据库 | 不污染环境，跑完即销毁 |
| data-testid | 选择器稳定，页面改版成本低 |
| Page Object | 操作复用，用例可读 |
| JSON Schema | 契约测试，字段类型变化能发现 |
| 数据库断言 | 防止接口假通过 |
| Allure 附件 | 失败可定位，不是只给一个红叉 |
| CI | 每次提交自动回归，体现工程化 |

## 14. 常见问题

### Q：为什么不用 unittest？

pytest 的 fixture、参数化、插件生态、断言失败信息都更好用。企业里 pytest 更常见。

### Q：为什么 UI 用例这么少？

UI 执行慢、容易受页面影响。能放接口层的规则尽量放接口层，UI 只验用户关键路径。这不是偷懒，是测试金字塔。

### Q：为什么不用随机断言/不写死金额？

金额是业务规则，必须写死预期值。比如 2 张桌垫 = 10000 分，QA10 减 1000 分，实付 9000 分。写死才能发现算错。

### Q：测试失败了怎么定位？

先看 Allure 的失败步骤和响应；接口问题看请求/响应/日志；UI 问题看截图和 HTML；数据问题查临时数据库。项目把这几样都保留了。

### Q：为什么不用 `time.sleep`？

UI 用 Playwright 自动等待 + 等待 URL/元素；接口本身是同步的。`sleep` 会让测试变慢且不稳定。

## 15. 推荐学习顺序

1. 先手工把 ShopLite 走一遍；
2. 打开 `tests/api/test_auth.py`，看懂一条用例；
3. 运行 `pytest tests/api/test_auth.py -v`；
4. 改一条 YAML 数据，再跑，看报告变化；
5. 打开 `pages/login_page.py`，看懂 Page Object；
6. 运行 `pytest tests/ui/test_login.py -v`；
7. 自己加一条“搜索无结果”的 UI 用例；
8. 最后看 `conftest.py`，理解 fixture 怎么把服务、用户、浏览器串起来。

不要一上来啃 `conftest.py`，先看用例，再看页面对象，最后看夹具。
